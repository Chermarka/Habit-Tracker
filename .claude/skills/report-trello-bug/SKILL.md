# Skill: report-trello-bug

Заводить баг-картку в Trello на дошці Habbit Tracker (https://trello.com/b/BpqgppeA/habbit-tracker), список **To Do**.

**Проактивна пропозиція:** це стосується не лише випадків, коли тебе прямо просять "заведи баг". Якщо в ході будь-якого аналізу (дебаг, ревʼю логів, розслідування помилки на прохання користувача з іншого приводу) ти доходиш висновку, що поведінка — це справжній баг (стабільний `500` або явне розходження з очікуваним результатом, а не коректно відхилений `400`), — запропонуй користувачу завести картку через цей скіл. Не пропускай це мовчки і не заводь картку без питання: спочатку запропонуй, і лише отримавши згоду, переходь до Кроку 0 нижче.

**Константи:**
- idList (To Do): `6a7496f310ba667987a5c422`
- index Elasticsearch: `habit-tracker-logs`
- Kibana base URL: `http://localhost:5601`
- Kibana index-pattern id (для "View single document"): `92646ae0-91a2-11f1-a0a2-3d64c86c6c17`
- Ключ і токен беруться з env vars `TRELLO_KEY` / `TRELLO_TOKEN` — ніколи не підставляй їх літеральні значення в команди чи текст, який потрапляє у видимий вивід

## Крок 0 — Без ідентифікатора скіл не запускається

Цей скіл НЕ шукає "чи є взагалі якісь помилки" наосліп — це та сама помилка, від якої застерігає промптинг у Модулі 1: без контексту агент або вигадає критерій сам, або мовчки обере одну з кількох можливих проблем.

**Потрібен хоча б один ідентифікатор від тестувальника:**
- uuid конкретного запису, АБО
- часовий діапазон ("щойно", "між 14:57 і 15:01"), АБО
- ендпоінт/дія ("не вдається відмітити прогрес звички"), АБО
- опис симптому користувача ("скарга: дашборд показує помилку")

**Якщо тестувальник дав тільки загальне "перевір, чи є помилки" — не переходь до Кроку 1.** Спочатку зроби широкий пошук (`log.responseStatus >= 400`, останні 10-15 хв), покажи короткий список кандидатів (час, endpoint, перший рядок помилки) і запитай, який саме мається на увазі. Заводити картку на здогад — гірше, ніж не завести взагалі.

## Крок 1 — Знайти помилку в логах

Маючи ідентифікатор з Кроку 0, шукай через `mcp__elasticsearch__search` в індексі `habit-tracker-logs` саме за ним (uuid / часове вікно / requestPath).

Для знайденого запису знайди **пару документів з однаковим `log.uuid`**:
- access-log — `requestMethod`, `requestPath`, `responseStatus`, `responseDuration`, `requestHeaders`
- error-log — той самий `uuid`, плюс `requestBody`, `stackTrace`

Перевір, чи помилка повторювалась (той самий stackTrace, різні uuid) — зафіксуй усі входження, це підсилює кейс.

**Перед тим як вважати це багом:** `responseStatus 400` найчастіше означає, що валідація коректно відхилила невалідні дані — це НЕ дефект. Багом варто заводити `500` або поведінку, що явно розходиться з очікуваною.

**Отримати `_id` документа з помилкою** (потрібен для посилання в Кроці 3): `mcp__elasticsearch__search` не завжди показує `_id` у текстовому виводі. Якщо не показав — доклич той самий запит напряму до Elasticsearch (`GET /habit-tracker-logs/_search`, той самий фільтр по `log.uuid`) і візьми `_id` з відповіді.

## Крок 3 — Сформувати опис за шаблоном

```
**Device:** {log.requestHeaders["sec-ch-ua-platform"] або порожньо}
**Environment:** stage
**User id:** {log.requestHeaders["x-user-id"] або "не знайдено"}
**Logs:** [View single document](http://localhost:5601/app/discover#/doc/92646ae0-91a2-11f1-a0a2-3d64c86c6c17/habit-tracker-logs?id={_id документа з помилкою})

**Передумови:**
{який стан/дані потрібні, щоб узагалі можна було відтворити баг — не інфо про саму помилку. Приклад: "Створена звичка 'Читати книгу' (NUMERIC, ціль 100)"}

**Кроки:**
1. {людською мовою, що користувач робив у застосунку — не HTTP-метод і не шлях}
2. {наступна дія, якщо в ланцюжку більше одного запиту}

**Актуальний результат:**
{error message або перший рядок stackTrace лога першопричини; якщо баг траплявся кілька разів — тут же, одним реченням: "стабільно відтворюється при X" — це спостереження про помилку, не передумова}

**Очікуваний результат:**
{що мало статися замість цього — якщо не очевидно з логів, запитай тестувальника}
```

**Як писати "Кроки" людською мовою, а не технічно:**

`requestMethod` + `requestPath` + `requestBody` — це сирі дані, а не текст для картки. Переклади їх у те, що користувач фізично робив у застосунку. Приклади перекладу:

| Технічний запит | Людська дія в "Кроки" |
| --- | --- |
| `POST /api/auth/login` | Увійшов у свій акаунт |
| `GET /api/habits` | Відкрив дашборд зі звичками |
| `GET /api/habits/week` | Відкрив вкладку "Тиждень" |
| `POST /api/habits` | Створив нову звичку |
| `PATCH /:id/checkin` з `completed` | Натиснув чекбокс на звичці |
| `PATCH /:id/checkin` з `value` | Ввів значення "{value}" для звички і підтвердив |
| `POST /:id/archive` | Заархівував звичку |

Якщо `x-user-id` присутній у заголовках — це підтверджує, що користувач уже був залогінений; можна почати кроки з "Увійшов у свій акаунт" навіть без окремого лога на `/auth/login`, якщо його немає в тому самому вікні часу.

**Не вигадуй кроки з "типового флоу" — перевіряй, що реально сталось.** Знайди суміжні запити того самого `x-user-id` у вузькому вікні часу навколо помилки (`GET /habit-tracker-logs/_search` за requestHeaders або `query_string` по userId, ±5-15 хв). Це потрібно, щоб не вигадати неправдиву дію (наприклад "увійшов в акаунт", якщо насправді сесія була активна ще з учора) — а не для того, щоб переказати все знайдене в картку.

**"Кроки" — мінімальний репродюс, а не хронологічний переказ сесії:**
- Не включай передумови, що не причетні до самого бага (реєстрація/вхід, що стались задовго до і ніяк не впливають на відтворення) — цьому місце в "Передумови", якщо взагалі потрібне, а найчастіше не потрібне зовсім
- Якщо той самий баг зловився кілька разів поспіль (наприклад -5, потім -99) — опиши **один** мінімальний крок, не кожну спробу окремо. Кількість повторів — це сигнал для "Актуальний результат" ("стабільно відтворюється"), не для "Передумови" і не окремі кроки
- Ціль — щоб хтось інший міг відтворити баг за лічені секунди, а не прочитати репортаж про сесію користувача

Приклад готових "Кроки" — мінімальний, перевірений, з технічним запитом для довідки:
```
**Кроки:**
1. Ввів значення "-99" для звички "Читати книгу" і підтвердив (`PATCH /api/habits/70dd4b21.../checkin {value: -99}`)
```
Технічний запит у дужках — не обов'язково, але корисно як довідка; головне, щоб основний текст кроку читався людською мовою і був мінімальним, а не переказом усього, що сталось у сесії.

**Правила:**
- Це прості текстові рядки "Label: значення" — без markdown-таблиці, без `|` і без розділювача `| --- | --- |`
- "Кроки" завжди людською мовою (що робив користувач у застосунку) — ніколи тільки HTTP-метод/шлях/тіло запиту без перекладу
- "Кроки" — мінімальний репродюс: без нерелевантних передумов (вхід/реєстрація, якщо вони не причина бага) і без повторення того самого збою кілька разів
- Кожен крок перевіряй проти реальних логів того самого `x-user-id` — не припускай "типовий флоу"; технічний запит можна додати поруч у дужках для довідки
- Порядок рядків завжди: Device → Environment → User id → Logs
- `Environment` завжди `stage` — не питай у тестувальника, навіть якщо застосунок насправді на `localhost`
- `sec-ch-ua-platform` приходить у лапках (напр. `"macOS"`) — прибери зайві escape-лапки перед вставкою
- Якщо `User id` не знайдено в заголовках (`x-user-id`) — залиш "не знайдено", рядок все одно включай (це реальний і корисний сигнал сам по собі)
- `Logs` — лише посилання "View single document", без тексту requestBody чи stackTrace в самій картці; увесь деталь — за посиланням
- Повний `stackTrace` у картку не копіюй — досить першого рядка в "Актуальний результат"
- "Передумови" — лише стан/дані, потрібні для відтворення (напр. яка звичка має існувати і якого типу); ніколи інформація про саму помилку чи її повторюваність
- Якщо баг траплявся кілька разів — згадай це в "Актуальний результат" ("стабільно відтворюється при..."), посилання в Logs веде на найновіший документ

## Важливі нюанси

- Ніколи не вставляй `TRELLO_KEY`/`TRELLO_TOKEN` як літеральні значення в команди чи повідомлення — тільки через `$TRELLO_KEY`/`$TRELLO_TOKEN`
- Якщо env vars не встановлені — зупинись і попроси тестувальника задати їх у своєму `~/.zshrc`, не питай значення напряму в чаті
- `Environment` — завжди `stage`, фіксоване значення, не питай і не підставляй `localhost`
- `Device` тут — це `sec-ch-ua-platform` з заголовків браузера (напр. `macOS`), не x-device-name як у мобільних застосунків — це веб-проєкт
- **Без ідентифікатора з Кроку 0 цей скіл не запускай.** "Заведи баг, якщо є помилки" без часу/ендпоінту/uuid — це промпт, на якому агент вгадує замість тестувальника. Один можливий кандидат серед кількох — це вибір, а не факт.
